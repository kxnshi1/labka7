# АгроМаркет — лабораторная работа №7

**Тема:** пользователи, JWT-аутентификация и разграничение доступа.

Проект продолжает лабораторную №6: каталог товаров и заявки хранятся в PostgreSQL, сервер предоставляет REST API, интерфейс написан на React. В лабораторной №7 добавлены регистрация, вход, роли `user` и `admin`, защита маршрутов и форма добавления товара для администратора.

## Технологии

- Backend: Node.js, Express 5, PostgreSQL, `pg`.
- Аутентификация: `bcryptjs`, `jsonwebtoken`.
- Защита: `express-rate-limit`, `helmet`, `cors`, проверка входных данных.
- Frontend: React, Vite, Fetch API, localStorage.
- Проверка API: Postman.

## Локальный запуск

Нужны Node.js с npm и работающий PostgreSQL. При выполнении работы использовались Node.js 24 и PostgreSQL 17. Команды ниже выполняются в PowerShell из корня проекта.

### 1. Настройка базы и сервера

Создайте пустую базу `agromarket` через pgAdmin, если её ещё нет.

```powershell
cd agromarket-server
npm install
```

Создайте `.env` в папке сервера. Пример структуры (значения-заглушки нужно заменить своими):

```dotenv
PORT=3000
DATABASE_URL=postgresql://postgres:YOUR_DB_PASSWORD@localhost:5432/agromarket
CORS_ORIGIN=http://localhost:5173
JWT_SECRET=YOUR_RANDOM_SECRET
JWT_EXPIRES_IN=2h
ADMIN_EMAIL=admin@agromarket.kz
ADMIN_PASSWORD=YOUR_ADMIN_PASSWORD
```

Пароль администратора должен содержать не менее 8 символов. Для генерации JWT_SECRET:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Вставьте полученную строку в `.env`. Специальные символы в пароле внутри DATABASE_URL должны быть URL-кодированы. В `.env.example` оставляйте только примеры без настоящих секретов.

При первом запуске инициализируйте таблицы:

```powershell
npm run db:init
npm run dev
```

**Важно:** `db:init` удаляет и заново создаёт таблицы, сбрасывает заявки и пользователей, загружает исходный каталог и создаёт администратора из `.env`. Для обычного повторного запуска используйте только `npm run dev`.

API: `http://localhost:3000`.

Проверка подключения: `GET http://localhost:3000/api/health`. При успешном подключении ответ содержит:

```json
{
  "status": "ok",
  "db": "connected"
}
```

Также сервер возвращает поле `time` с временем проверки.

### 2. Запуск интерфейса

В другом окне PowerShell из корня проекта:

```powershell
cd agromarket-react
npm install
npm run dev
```

Откройте `http://localhost:5173`. Адрес API задаётся через `API_URL` в `src/api.js` и должен указывать на локальный backend с префиксом `/api`. Если Vite запустился на другом порту, согласуйте адрес интерфейса с CORS_ORIGIN и перезапустите сервер.

Для входа администратора используйте ADMIN_EMAIL и ADMIN_PASSWORD, с которыми была выполнена инициализация базы. Простое изменение ADMIN_PASSWORD в `.env` не изменяет хэш уже созданной учётной записи.

## API

Базовый адрес: `http://localhost:3000`. Для защищённых запросов используется заголовок `Authorization: Bearer <token>`.

| Метод | Маршрут | Доступ | Основные ответы |
| --- | --- | --- | --- |
| GET | /api/health | Все | 200, 500 |
| POST | /api/auth/register | Все | 201, 400, 409 |
| POST | /api/auth/login | Все | 200, 400, 401, 429 |
| GET | /api/auth/me | С токеном | 200, 401, 404 |
| GET | /api/products | Все | 200 |
| GET | /api/products/:id | Все | 200, 400, 404 |
| POST | /api/products | admin | 201, 400, 401, 403 |
| PUT | /api/products/:id | admin | 200, 400, 401, 403, 404 |
| DELETE | /api/products/:id | admin | 204, 400, 401, 403, 404 |
| POST | /api/orders | Все | 201, 400 |
| GET | /api/orders | admin | 200, 401, 403 |
| PATCH | /api/orders/:id | admin | 200, 400, 401, 403, 404 |

Для поиска товаров: `/api/products?search=яблоки`. Для JSON-запросов нужен `Content-Type: application/json`. Дополнительно возможны `413` для слишком большого тела и `500` при внутренней ошибке.

Регистрация принимает `name`, `email`, `password`; вход — `email`, `password`. Оба успешных запроса возвращают `{ user, token }`. Поле `password_hash` клиенту не передаётся. Email нормализуется в нижний регистр.

Пример создания товара:

```json
{
  "name": "Яблоки",
  "category": "Фрукты",
  "price": 500,
  "unit": "кг",
  "image": "/images/apples.svg"
}
```

Название обязательно, цена должна быть целым неотрицательным числом. Для заявки обязательны имя, email и целое количество не менее 10. Допустимые статусы заявки: `new`, `processing`, `done`, `cancelled`.

Пример изменения статуса:

```json
{ "status": "processing" }
```

## Как устроена защита

Пароль хэшируется bcrypt перед записью в users.password_hash. При входе используется bcrypt.compare. JWT содержит идентификатор пользователя в `sub`, роль и временные поля. Подпись проверяется на сервере с JWT_SECRET.

Middleware requireAuth проверяет токен и заполняет req.user. Следующий middleware requireRole('admin') проверяет роль. Отсутствующий или недействительный токен даёт 401; действительный токен без нужных прав — 403.

React сохраняет токен в localStorage и отправляет его через apiFetch. При загрузке страницы профиль запрашивается через `/api/auth/me`. Выход удаляет локальные данные пользователя и токен. Обработчик 401 для защищённых запросов очищает сохранённую авторизацию. Форма добавления товара отображается только администратору; сервер независимо проверяет доступ.

На вход настроен лимит: 5 неуспешных попыток за 15 минут с одного IP, затем 429. Счётчик хранится в памяти процесса. Helmet добавляет защитные HTTP-заголовки. Размер JSON-тела ограничен 10 КБ. Ошибочный JSON возвращает 400, превышение размера — 413. SQL-запросы используют параметры.

localStorage доступен JavaScript, поэтому XSS может привести к краже токена. Выход из интерфейса удаляет локальную копию, но не отзывает уже выпущенный JWT на сервере: он действует до истечения срока.

## Postman и результаты проверок

Путь для экспортированной коллекции: `agromarket-server/postman/agromarket.postman_collection.json`.

Для повторной проверки сначала выполните вход администратора и вход обычного пользователя. Скрипты After response сохраняют их токены в переменные коллекции `token` и `userToken`. В Bearer Token используйте соответственно `{{token}}` или `{{userToken}}`; для проверки без авторизации выберите No Auth.

| Проверка | Результат ручной проверки |
| --- | --- |
| Подключение API к PostgreSQL | 200, db: connected |
| Успешная регистрация | 201, роль user |
| Повторная регистрация с занятым email | 409 |
| Успешный вход | 200, пользователь и токен |
| Просмотр заявок администратором | 200 |
| Просмотр заявок без токена | 401 |
| Просмотр заявок обычным пользователем | 403 |
| Регистрация с полем role: admin | Назначена роль user |
| Пароль регистрации из трёх символов | 400 |
| Вход с неверным паролем | 401 |
| Запрос с fake.invalid.token | 401 |
| Некорректный JSON | 400 |

Проверены вход через интерфейс, отображение формы товара для администратора, добавление товара и сохранение входа после обновления страницы.

Проверка истечения JWT через 30 секунд, срабатывания 429, сравнение времени bcrypt при разных cost, проверка OPTIONS и заголовков, превышение лимита тела и порча токена в localStorage отдельно не завершены или не зафиксированы. Полный успешный прогон коллекции Runner не подтверждён. Проверка строки `fake.invalid.token` подтверждает отклонение некорректного токена, но не заменяет эксперимент с изменением payload настоящего JWT.

## Лабораторная 7 — ответы

**Одинаковые ли хэши у пользователей с одним паролем?**

Обычно нет: bcrypt создаёт случайную соль для каждого хэширования. Соль и параметр сложности включены в сохранённую строку, поэтому compare может проверить пароль. Это объяснение алгоритма; отдельный эксперимент со сравнением двух хэшей в этой работе не зафиксирован.

**Что вернул сервер при регистрации с role: admin?**

Пользователь получил роль `user`. Обработчик не берёт роль из тела запроса, а база применяет DEFAULT 'user'.

**Почему нельзя подделать токен, изменив роль?**

Подпись зависит от заголовка и payload. Изменение role без пересчёта подписи с секретным ключом делает токен недействительным. JWT подписан, но его содержимое не зашифровано. Проверка изменения payload на jwt.io отдельно не проводилась; проверен отказ для некорректного токена.

**Что произойдёт при порче токена в localStorage?**

Ожидается 401 при следующем защищённом запросе, после которого клиент очистит авторизацию. Эксперимент в браузере отдельно не проводился.

**Почему спрятать кнопку в React недостаточно?**

Пользователь может отправить запрос напрямую через Postman или другой клиент. Поэтому права проверяются на сервере перед выполнением операции.

**Использовался ли ИИ и для чего?**

Использовался ChatGPT: для пошаговых объяснений, подготовки и исправления кода Express и React, диагностики подключения к PostgreSQL и синтаксических ошибок, настройки Postman и оформления README. Запуск приложения и ручные проверки выполнялись локально.

## Краткие ответы для защиты

1. **Аутентификация** устанавливает личность пользователя; ошибка — 401. **Авторизация** проверяет разрешение на действие; недостаточно прав — 403.
2. Хэширование позволяет проверять пароль без хранения обратимо восстанавливаемого значения. Соль мешает использовать готовые таблицы хэшей, а вычислительная сложность bcrypt замедляет перебор. Слабые пароли всё равно могут быть подобраны.
3. JWT состоит из header, payload и signature. Header и payload можно декодировать без секрета; секрет нужен для создания корректной подписи.
4. При утечке JWT_SECRET злоумышленник сможет подписывать собственные токены, в том числе с ролью admin. Ключ нужно заменить, после чего старые токены перестанут проходить проверку.
5. requireAuth проверяет JWT. requireRole возвращает middleware, запоминающий требуемую роль через замыкание. Порядок вызова: сначала requireAuth, затем requireRole.
6. Общее сообщение о неверных данных входа не раскрывает, существует ли указанный email.
7. Mass assignment — неконтролируемое присваивание полей из запроса. Защита в routes/auth.js: при INSERT перечислены разрешённые поля, role из req.body не используется.
8. Токен хранится в localStorage и передаётся в Authorization. При выходе удаляется. Основной риск — доступ к нему при XSS.
9. Интерфейс не является границей безопасности; проверка прав обязательна на API.
10. Preflight — предварительный OPTIONS-запрос браузера для проверки разрешения межсайтового запроса. В частности, его вызывают Authorization и Content-Type: application/json. Middleware cors обрабатывает разрешения; CORS не заменяет авторизацию и не блокирует Postman.

## Границы реализации и публикация

Бонусные функции — личные заявки, смена пароля, панель заявок в React и кнопка удаления товара — в рамках этой версии не заявлены. Столбец orders.user_id подготовлен в схеме, но привязка заявок к вошедшему пользователю не реализована.

В репозиторий включаются исходники, package.json и lock-файлы, SQL-схема, .env.example и коллекция Postman. Настоящий .env, node_modules, пароли и действующие токены публиковать не следует. Перед экспортом коллекции для GitHub очистите значения токенов, сохранённые ответы с токенами и реальные пароли; для повторного запуска используйте локальные переменные.
